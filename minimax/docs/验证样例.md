# 验证样例

本样例用一个真实可运行、具备测试的业务工程 `demo_shop/`，完成一次局部修改：
为订单筛选增加客户等级分组过滤。

## 1. 任务描述

> 为订单筛选增加客户等级分组过滤：`customer_tiers` 中的 `premium` 分组必须展开为 `gold` 与 `silver`。

**要改什么**

- `demo_shop/src/shop/filters.py` 中的 `filter_orders` 需要识别等级分组。
  当 `OrderCriteria.customer_tiers` 中出现 `premium` 时，它代表 `gold` 与 `silver` 两个具体等级，
  过滤时按展开后的等级集合判断。

**哪些原有行为必须保持不变**

| 规格 | 必须保持的行为 |
| --- | --- |
| `SPEC-FILTER-001` | 按 `status` 过滤；空 `status` 返回全部订单；不改变输入顺序，不修改输入对象 |
| `SPEC-FILTER-002` | 按 `min_amount` 过滤；金额比较使用订单自身的 `Decimal` 金额 |
| — | 具体等级仍然精确匹配：`customer_tiers={"gold"}` 只返回 `gold` 订单 |
| — | 空 `customer_tiers` 不按等级过滤 |
| — | 分组与具体等级可以混合使用 |
| `SPEC-PRICE-010` | 阶梯折扣计算的门槛、折扣率与量化精度 |

## 2. 有效规格

| 规格 | 标题 | 适用范围 |
| --- | --- | --- |
| `SPEC-FILTER-001` | 订单状态筛选 | `src/shop/filters.py` |
| `SPEC-FILTER-002` | 订单金额下限筛选 | `src/shop/filters.py` |
| `SPEC-FILTER-003` | 客户等级分组筛选 | `src/shop/filters.py` |
| `SPEC-PRICE-010` | 阶梯折扣计算 | `src/shop/pricing.py` |

规格文档位于 `specs/`，每一份文档的标题行携带规格编号，模块按该编号建立条目。
`SPEC-FILTER-003` 的更新版本位于 `specs/updates/SPEC-FILTER-003.v2.md`。

## 3. 初始数据

导入命令把以下资料写入嵌入式 seekDB：

| 资料 | 数量 | 内容 |
| --- | --- | --- |
| 规格条目 | 4 | 编号、标题、需求正文、适用范围、来源文件与行号、内容哈希、版本 |
| 代码符号 | 23 | 函数与类的名称、种类、行号范围与源码片段 |
| 测试用例 | 17 | 测试名、文件、行号，以及测试体引用到的符号 |

导入的输入：

- 规格：`specs/*.md`
- 业务工程：`demo_shop/`（`src/shop/*.py` 与 `tests/test_*.py`）

## 4. 操作步骤

```bash
# 0. 把业务代码还原到修改前的状态
python verify/reset_code.py

# 1. 导入资料到 seekDB
python -m sddctx import

# 2. 组装开发上下文
python -m sddctx context \
  --task "为订单筛选增加客户等级分组过滤：customer_tiers 中的 premium 分组必须展开为 gold 与 silver" \
  --task-id task-filter-003

# 3. 修改前执行目标测试与回归测试
demo_shop/.venv/bin/python -m pytest tests/test_filters_tier_groups.py -v
demo_shop/.venv/bin/python -m pytest tests/test_filters_regression.py tests/test_pricing.py -v

# 4. 由 MiniMax 修改代码并应用差异
python -m sddctx apply \
  --task "为订单筛选增加客户等级分组过滤：customer_tiers 中的 premium 分组必须展开为 gold 与 silver" \
  --task-id task-filter-003 \
  --project demo_shop \
  --python demo_shop/.venv/bin/python \
  --tests tests/test_filters_tier_groups.py

# 5. 修改后执行同一组测试
demo_shop/.venv/bin/python -m pytest tests/test_filters_tier_groups.py -v
demo_shop/.venv/bin/python -m pytest tests/test_filters_regression.py tests/test_pricing.py -v

# 6. 从 PowerContext 读回任务状态
python -m sddctx state show --task-id task-filter-003

# 7. 重启模块，用复用的状态重新组装上下文
python -m sddctx context --task "..." --task-id task-filter-003

# 8. 更新规格、重新导入，确认上下文使用更新后的内容
python verify/apply_spec_update.py --apply
python -m sddctx import
python -m sddctx context --task "..." --task-id task-filter-003
python verify/apply_spec_update.py --reset
python -m sddctx import
```

一次跑完全部步骤：

```bash
python verify/run_verification.py
```

## 5. 预期结果

### 5.1 上下文输出必须定位到的来源

`context` 的输出包含四部分，每一项都指向真实存在的文件与行号：

| 部分 | 内容 | 本样例中的值 |
| --- | --- | --- |
| 适用的规格条目 | 编号、标题、版本、来源文件与行号、需求正文 | `SPEC-FILTER-003`（`specs/SPEC-FILTER-003.md:1`）、`SPEC-FILTER-001` |
| 需要修改的代码文件或符号 | 文件、行号范围、种类、名称 | `src/shop/filters.py` 的 `OrderCriteria` 与 `filter_orders` |
| 用于验证的测试 | 文件、行号、测试名 | `tests/test_filters_tier_groups.py` 与 `tests/test_filters_regression.py` 中的 12 个测试 |
| 已完成事项、待办事项和已有验证结果 | 来自 PowerContext 的任务状态 | 见 5.4 |

完整输出见 `artifacts/context.json`。

### 5.2 修改前：目标测试失败，回归测试通过

```
$ demo_shop/.venv/bin/python -m pytest -v tests/test_filters_tier_groups.py
FAILED tests/test_filters_tier_groups.py::test_premium_group_expands_to_gold_and_silver
FAILED tests/test_filters_tier_groups.py::test_group_and_exact_tier_can_be_combined
2 failed, 2 passed
```

失败原因是断言不成立（`AssertionError: assert [] == ['o-1', 'o-2', 'o-5']`），
即目标行为尚未实现，不是依赖缺失或启动失败。

回归测试在修改前后都通过：

```
$ demo_shop/.venv/bin/python -m pytest -v tests/test_filters_regression.py tests/test_pricing.py
13 passed
```

日志见 `artifacts/logs/03-before-target-tests.log` 与 `artifacts/logs/04-before-regression-tests.log`。

### 5.3 修改后：同一组测试全部通过

```
$ demo_shop/.venv/bin/python -m pytest -v tests/test_filters_tier_groups.py
4 passed
$ demo_shop/.venv/bin/python -m pytest -v tests/test_filters_regression.py tests/test_pricing.py
13 passed
```

测试集在修改前后完全一致，没有删除断言、跳过测试或修改预期结果。
日志见 `artifacts/logs/06-after-target-tests.log` 与 `artifacts/logs/07-after-regression-tests.log`。

代码差异见 `artifacts/applied.patch`，修改前后的代码快照见
`artifacts/code-snapshot-before/` 与 `artifacts/code-snapshot-after/`。

### 5.4 任务状态能够复用

修改完成后，模块把任务状态写入 PowerContext：

- work contract：目标、事实、范围、排除项、完成条件
- task outcome：已完成事项、校验结果、待办事项
- 一条原子记忆：本次任务的摘要

重启模块后（重新启动进程），`state show` 与 `context` 都能读回这些内容，
并把它带进下一次组装出的上下文。读回结果见 `artifacts/powercontext-state.md`，
复用的上下文见 `artifacts/context-reused-state.json`。

### 5.5 规格更新后使用更新后的内容

应用更新后的规格（新增 `standard` 分组），重新导入后，模块检索到的规格条目
版本号增加，需求正文包含新增的分组：

| 时机 | 版本 | 需求正文包含 `standard` 分组 |
| --- | --- | --- |
| 更新前 | 1 | 否 |
| 更新后 | 递增 | 是 |

对比文件：`artifacts/context.json` 与 `artifacts/context-after-spec-update.json`。
这说明上下文来自数据库中存储的资料，而不是固定答案。

## 6. 重置方法

| 内容 | 方法 |
| --- | --- |
| 业务代码 | `python verify/reset_code.py` |
| 规格 | `python verify/apply_spec_update.py --reset` |
| seekDB 资料 | 删除 `SDDCTX_DB_DIR` 目录后 `python -m sddctx import` |
| PowerContext 状态 | 停止 Server，删除其用户数据目录中的 SQLite 数据库，重新启动 |
| 全部 | 依次执行上表四行 |

## 7. 上下文模块的调用入口与输入输出

入口：`python -m sddctx <子命令>`（安装后为 `sddctx <子命令>`）。

| 子命令 | 输入 | 输出 |
| --- | --- | --- |
| `import` | `--specs` 规格目录、`--project` 业务工程根目录 | JSON：导入条数、发生变化的规格编号、规格编号列表 |
| `context` | `--task` 任务描述、`--task-id` 任务编号、`--limit` 规格条数上限 | 文本或 `--json` 输出：规格、代码、测试、复用的状态 |
| `apply` | `--task`、`--task-id`、`--project`、`--python`、`--tests`、`--record`、`--diff-output`、`--prompt-output`、`--raw-output` | 变更文件列表、各测试选择的退出码、技术记录 JSON、差异文件、提示词文件 |
| `state save` | `--file` 状态 JSON | JSON：写入的 Source id |
| `state show` | `--task-id` | JSON：目标、事实、范围、排除项、已完成、待办、校验结果、Source id |
| `run` | 同 `apply` | 同 `apply` |

退出码：

| 退出码 | 含义 |
| --- | --- |
| 0 | 成功 |
| 2 | 没有规格匹配到该任务 |
| 3 | 模型回答中没有 unified diff |
| 4 | 差异无法应用到工作区（上下文对不上时拒绝写入） |
| 5 | 有测试选择未通过 |
| 6 | PowerContext 中没有该任务的状态 |
| 7 | 规格目录或业务工程目录不存在（检查 `SDDCTX_ROOT`） |
| 8 | 规格目录中没有规格文档 |
