# 一页技术说明

## 模块结构

```text

├── sddctx/                      上下文模块
│   ├── cli.py                   命令行入口：import / context / apply / state / run

│   ├── store.py                 seekDB 存储与查询层
│   ├── ingest.py                规格、代码符号与测试的解析和导入
│   ├── retrieve.py              任务相关资料的选择与上下文组装
│   ├── agent.py                 提示词构造、测试执行、任务状态构造
│   ├── minimax_client.py        MiniMax Messages API 客户端
```

## 上下文选择方式

选择分两层，两层的信号都来自 seekDB 的实际查询结果。

**第一层：选中适用的规格条目。**

1. 从任务描述中抽取标识符（`filter_orders`、`customer_tiers`、`premium`）与中文短语。
2. 标识符走 seekDB 的全文索引 `MATCH(search_text) AGAINST (... IN BOOLEAN MODE)`，
   返回带相关度的规格条目。
3. 中文短语走 `LIKE` 匹配，因为 seekDB 的默认分词器按空白切分，中文无法命中全文索引。
4. 两类信号合并后按相关度排序，取前 N 条。

**第二层：由规格的适用范围决定代码与测试。**

规格在 `## 适用范围` 中声明它约束的源文件。模块按该路径取出：

- 代码符号：路径下的函数与类，含行号范围与源码片段；
- 测试用例：函数体引用了这些符号的测试，含文件、行号与测试名；
- 文件全文：需要修改的文件的完整内容，保证模型看到的是文件当前的样子。

**输出内容。** 上下文包含适用的规格条目（编号、版本、来源文件与行号、需求正文）、
需要修改的代码文件或符号、用于验证功能及兼容性的测试，以及从 PowerContext 读回的
已完成事项、待办事项和已有验证结果。

## 各项技术的分工

| 技术 | 承担的作用 | 落在哪里 |
| --- | --- | --- |
| **MiniMax** | 参与本次任务的代码生成与修改。模块把规格、完整文件内容与测试组装成提示词，MiniMax 返回 unified diff，模块应用差异并执行测试 | `sddctx/minimax_client.py`、`sddctx/agent.py`、`sddctx/patch.py` |
| **seekdb** | 存储工程资料与索引：规格条目、代码符号、测试用例、规格修订历史、导入记录。检索结果直接用于构造任务上下文 | `sddctx/store.py`、`sddctx/ingest.py`、`sddctx/retrieve.py` |
| **PowerContext** | 保存任务进展与验证结果：work contract（目标、事实、范围、排除项、完成条件）、task outcome（已完成事项、校验结果、待办事项）与原子记忆。模块重启后读回并用于后续上下文 | `sddctx/state.py` |

三项技术的边界是明确的：seekDB 管资料，PowerContext 管状态，MiniMax 管代码。

## 数据流

```text
规格 / 代码 / 测试
        │
        ▼  import
   嵌入式 seekDB ─────────────────────────┐
        │                                │
        │  检索：全文索引 + 适用范围关联    │
        ▼                                │
   开发上下文（规格 + 代码 + 测试） ◄──────┘
        │
        ├──► PowerContext：读回上一次的任务状态
        │
        ▼
   MiniMax Messages API → unified diff → 应用到业务工程 → 执行测试
        │
        ▼
   PowerContext：写入 work contract / task outcome / 原子记忆
        │
        ▼
   模块重启 → 读回状态 → 重新组装上下文
```

## 关键设计取舍

- **资料与状态分开存放。** seekDB 保存的是工程资料，PowerContext 保存的是任务状态。
  两者回答的问题不同：前者回答"这段代码应该遵守什么"，后者回答"这项工作做到哪里了"。
- **选择可追溯。** 每条规格都记录来源文件与行号，每条测试都记录它引用了哪些符号，
  因此输出的每一条来源都可以在仓库中核对。
- **规格可演进。** 规格按内容哈希判断是否变化，变化时版本递增并保留修订历史。
  重新导入后，检索到的就是更新后的内容。
- **差异应用是保守的。** 上下文对不上时拒绝写入，不会留下半应用的文件；
  行号不可靠时按上下文块在附近定位。
- **状态在模块之外。** 任务状态保存在 PowerContext Server，模块进程重启后重新读回，
  状态本身不依赖模块的进程生命周期。
